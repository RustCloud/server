# Возможности сервера для плагинов: `use.*`

Тяжёлый нативный код, который сервер выполняет **для** плагина, вне песочницы WASM: ffmpeg,
нейросети (ONNX) и другое. Каждая возможность — отдельный импорт WIT и отдельное
разрешение, которое утверждает администратор. Список будет расти; каждая новая описывается здесь.

| Возможность | Импорт WIT        | С версии API | Что даёт                                                   |
|-------------|-------------------|--------------|------------------------------------------------------------|
| `use.ffmpeg` | `use-ffmpeg`     | 0.2.7        | метаданные фото, видео и музыки; миниатюры                 |
| `use.onnx`   | `use-onnx`       | 0.2.13       | нейросети ONNX из хранилища плагина: лица, эмбеддинги текста, звук |

## Как плагин получает возможность

```toml
# manifest.toml
api = "^0.2.7"

[permissions]
use = ["ffmpeg"]
```

- Администратор видит «Возможности: use.ffmpeg» в строке прав плагина и утверждает их, включая
  плагин, как доступ к файлам и сеть. Обновление, которое добавило возможность, отключает плагин
  до подтверждения.
- Без разрешения вызовы отвечают `not-allowed`; на сервере без инструмента — `unsupported`
  (заранее — через `get-capabilities`). Плагину, который возможность не вызывает, её импорт не
  нужен: в собранный `app.wasm` попадают только используемые импорты, и он загружается на любом
  сервере с подходящей версией API.
- Собирается плагин без кода сервера: нужен только `app.wit` нужной версии и `wit-bindgen`
  ([свой плагин](plugins.md#свой-плагин-на-rust)).

## Как сервер защищает себя

Плагину не доверяют, файлам пользователей — тоже: в ffmpeg миллионы строк C, а у его форматов
есть возможности, которые сами по себе опасны (плейлисты, читающие чужие файлы). Поэтому:

1. **Плагин просит намерение, а не команду.** В WIT только перечисления и числа в пределах:
   «миниатюра 320×320, WebP, качество 80». Ни одна строка плагина не попадает в командную
   строку — её из шаблона собирает сервер ([picture.rs](../../crates/media/src/picture.rs)).
2. **Инструмент не видит путей.** Сервер сам открывает файл после обычной проверки доступа
   (файл пользователя — в пределах выданного плагину, AppData — пользователя запроса, хранилище —
   самого плагина) и передаёт его ffmpeg как открытый на чтение дескриптор (`-i fd:`); результат
   идёт через трубу. Разрешён только протокол `fd` (`-protocol_whitelist fd`).
3. **Своя сборка ffmpeg** ([docker/build-ffmpeg.sh](../../docker/build-ffmpeg.sh)): статическая,
   LGPL, `--disable-everything --disable-network --disable-autodetect` и только нужные форматы,
   кодеки и фильтры. Чего нет в бинарнике, того не атаковать. Кодировщик H.264 — OpenH264 (BSD),
   собран из исходников: патентная лицензия Cisco распространяется только на их бинарники.
4. **Отдельный процесс в песочнице** ([crates/sandbox](../../crates/sandbox/src/lib.rs)): сервер
   запускает себя как `rustcloud sandbox`, тот ограничивает себя и становится ffmpeg:
   - rlimits — память и процессор `[media]`, запись файлов запрещена, без дампов памяти;
   - `no_new_privs`;
   - seccomp — нельзя открыть, создать, переименовать или удалить файл, создать сокет, запустить
     процесс (только потоки), послать сигнал не себе, `ptrace`, `mount`, пространства имён, BPF,
     `io_uring`, модули ядра. Даже взломанный ffmpeg не прочитает чужой файл и не выйдет в сеть:
     нужных системных вызовов у него просто нет;
   - Landlock — дополнительно, где ядро его включает (на ядре Proxmox — нет).

   Какие слои действуют на этом сервере, видно на вкладке «Плагины».
5. **Сначала разбор, потом работа.** Перед миниатюрой файл разбирается, и слишком большой
   (больше `[media] max_megapixels`) отклоняется до тяжёлой работы; ffmpeg получает `-max_pixels`.
   Результат проверяется: нужный формат, не больше [предела данных](plugins.md#лимиты) плагина.
6. **Свои пределы:** `[media] workers` процессов одновременно, время и память на процесс
   ([настройки](../configuration.md#media)).
   - Фоновые задачи занимают все процессы, кроме одного: он всегда остаётся для запросов из
     интерфейса, и индексация большой библиотеки не заставляет ждать открытое фото.
   - Запрос ждёт свободный процесс до 10 с, потом `busy`. Порция задач ждёт до 5 минут, потом
     `busy` (верните `retry`, задача повторится позже).
   - Время ffmpeg — ожидание и работа — не входит ни в работу плагина, ни в общее время вызова:
     порция из сотни миниатюр не упирается в 60 с.

Метаданные фото (дата, место, камера) читает не ffmpeg, а `nom-exif` — разбор на Rust,
безопасный по памяти, прямо в сервере. Превью RAW находит свой разбор тегов TIFF и боксов CR3
([raw.rs](../../crates/media/src/raw.rs)), тоже на Rust: каждое смещение проверяется по размеру
файла, ffmpeg получает только сам JPEG через трубу. У RAW `get-metadata` отвечает без ffprobe:
`container` — `cr2`, `nef`, `dng`…, размер — у превью, камера и дата — из тегов.

## `use.ffmpeg`

```rust
use rustcloud::app::use_ffmpeg::{self, Fit, ImageFormat, PictureOptions, Source};

let caps = use_ffmpeg::get_capabilities();          // caps.available, caps.image_formats…
let info = use_ffmpeg::get_metadata(&Source::File(file_id))?;
// info.container ("jpeg", "heif", "mp4"…), info.still, info.width/height (с поворотом),
// info.duration_ms, info.taken_at, info.location, info.camera_make/model, info.lens,
// info.video/audio/subtitles, info.tags ("exif.ISO" → "200")

let thumb = use_ffmpeg::thumbnail(&Source::File(file_id), PictureOptions {
    max_width: 320, max_height: 320, fit: Fit::Cover, format: ImageFormat::Webp,
    quality: 80, at_ms: None,                         // видео: типичный кадр после начала
})?;                                                  // байты картинки, до предела данных
```

- **Источник:** `file(id)` — файл пользователя, выданный плагину; `appdata(path)` — файл AppData
  пользователя запроса; `storage(path)` — файл хранилища плагина. Без пользователя (фоновая задача
  без него, анонимный запрос) — только `storage`.
- **Читает:** JPEG, PNG, WebP, GIF, BMP, TIFF, HEIC/HEIF, AVIF; RAW — CR2, CR3, NEF, ARW, RAF, RW2,
  ORF, DNG, PEF и другие на TIFF: по JPEG, который камера кладёт в файл (обычно в полный размер, у
  CR3 и ARW — 1620×1080 или около того), повёрнутому, как держали камеру; видео H.264, HEVC, VP8, VP9, AV1,
  MPEG-4, MPEG-2 в MP4/MOV, MKV/WebM, AVI, TS, FLV; звук AAC, MP3, Opus, Vorbis, FLAC, ALAC, PCM.
  Пишет миниатюры JPEG, WebP, PNG; потоки видео — H.264 (OpenH264) и AAC во фрагментах MP4
  ([Видео](plugins.md#видео)).
- **Ошибки:** `no-user`, `not-allowed`, `not-found`, `unsupported(…)`, `invalid-options(…)`
  (рамка 0 или больше 8192, качество 0), `busy`, `timeout`, `failed(причина)` — битый файл или
  больше пределов сервера.

Дальше (см. [ROADMAP](../../ROADMAP.md#плагины)): `convert-image` в AppData или хранилище,
раскадровка; перекодирование — долгими задачами.

## `use.onnx`

Нейросети в формате ONNX: распознавание лиц, эмбеддинги текста и картинок, классификаторы,
распознавание речи — любая модель, которую умеет [tract](https://github.com/sonos/tract)
(движок на Rust, без C++). Модель — файл [хранилища плагина](plugins.md#хранилище-плагина),
обычно его скачивает сервер по `[[downloads]]` манифеста; плагин называет её путём.

```toml
# manifest.toml
api = "^0.2.13"

[permissions]
use = ["onnx"]
network = ["huggingface.co", "*.huggingface.co", "*.hf.co"]

[[downloads]]
path = "models/det_500m.onnx"
url = "https://huggingface.co/…/det_500m.onnx"
sha256 = "…"
```

```rust
use rustcloud::app::use_onnx::{self, *};

let caps = use_onnx::get_capabilities();     // caps.available, caps.engine, caps.keep_loaded_seconds
let info = use_onnx::get_model_info("models/det_500m.onnx")?;
// info.inputs: [{name: "input.1", dtype: Some(F32), shape: [Some(1), Some(3), None, None]}], info.outputs…

// Фото как вход модели: 640×640, целиком, остаток — чёрный, (v − 127.5) / 128.
let options = ImageOptions {
    width: 640, height: 640, fit: ImageFit::Inside, crop: None,
    channels: Channels::Rgb, layout: Layout::Nchw,
    mean: (127.5, 127.5, 127.5), std: (128.0, 128.0, 128.0),
};
let picture = use_onnx::image_tensor(&Source::File(file_id), options)?;
// picture.width/height — размер фото, как его видят: масштаб = min(640 / width, 640 / height).
let outputs = use_onnx::run("models/det_500m.onnx", &[NamedTensor {
    name: "input.1".into(), tensor: picture.tensor,
}])?;                                         // выходы в порядке модели, с именами

// Найденное лицо — вторым вызовом, кропом в пикселях фото, для модели эмбеддингов.
let face = use_onnx::image_tensor(&Source::File(file_id), ImageOptions {
    width: 112, height: 112, fit: ImageFit::Stretch,
    crop: Some(Crop { x: 410, y: 120, width: 180, height: 180 }), ..options
})?;

// Текст: токены делает плагин, модель получает i64.
let ids = Tensor { dtype: TensorType::I64, shape: vec![1, n], data: bytes_of(&token_ids) };

// Звук: моно f32 с нужной частотой, отрезок по времени.
let speech = use_onnx::audio_tensor(&Source::File(file_id), AudioOptions {
    rate: 16000, start_ms: 0, duration_ms: Some(30_000),
})?;                                          // f32 [samples]
```

- **`run`** принимает и отдаёт любые тензоры: `f32`, `f64`, `i32`, `i64`, `i8`, `u8`, `bool`,
  значения little-endian подряд, последний индекс меняется быстрее всех. Входы сопоставляются
  с моделью по имени, в любом порядке. Измерения, которые модель оставила открытыми (`None` в
  `shape`: батч, длина текста), задаёт вход. Неверное имя, тип или размер — `invalid-input` с
  понятной причиной («input.1: dimension 1 must be 3, not 4»).
- **Помощники.** `image-tensor` делает вход из фото любого формата (HEIC и RAW тоже, повёрнутого,
  как держали камеру) или кадра видео: точный размер, `stretch`, `inside` (целиком в левом верхнем
  углу, остаток чёрный) или `cover`, кроп, порядок цветов, раскладка `nchw`/`nhwc` и нормализация
  `(v − mean) / std`. `audio-tensor` даёт моно `f32` с частотой 8000–48000 из музыки, записи или
  видео. Помощникам нужен ffmpeg на сервере (но не разрешение `use.ffmpeg`).
- **Модель загружается один раз и остаётся в памяти.** Первый вызов загружает её в отдельный
  процесс (это дольше всего), следующие идут сразу. Модель выгружается через
  `[onnx] keep_loaded_seconds` (по умолчанию 5 минут) после последнего вызова, так что порция
  задач по сотне фото загружает её один раз. Одновременно загружено до `[onnx] workers` моделей
  (по умолчанию 4); новая вытесняет ту, что дольше всех не использовалась. Вызовы одной модели
  идут по очереди. Обновлённый файл (другая `sha256`) загружается заново; модели удалённого плагина
  выгружаются сразу.
- **Пределы:** вход и выход за вызов — не больше [предела данных](plugins.md#лимиты) плагина;
  модель — до `[onnx] max_model_mib`; время одного вызова — `[onnx] time_seconds`, и оно, как
  ожидание очереди, не входит во время плагина. Запрос ждёт очередь модели до 30 с, порция задач —
  до 5 минут, потом `busy` (в задаче верните `retry`).
- **Ошибки:** `no-user` (помощник с `file`/`appdata` без пользователя), `not-allowed`,
  `not-found`, `unsupported(…)`, `invalid-input(…)`, `busy`, `timeout`, `failed(причина)` —
  модель не загрузилась (не ONNX, операция, которой нет в tract, не хватило памяти) или результат
  больше предела. Проверены детектор лиц SCRFD и ArcFace (insightface `buffalo_s`),
  all-MiniLM-L6-v2; Silero VAD v5 tract 0.23 не загружает.

**Защита.** Модель — такой же недоверенный ввод, как файл пользователя: её разбор и запуск идут
в отдельном процессе `rustcloud onnx-worker`, который ограничивает себя
([`confine_self`](../../crates/sandbox/src/lib.rs)) до того, как прочитает первый байт: те же
rlimits (память `[onnx] memory_mib`), `no_new_privs`, seccomp и Landlock, что у ffmpeg, но без
доступа к файловой системе вовсе. Модель и тензоры идут через трубу; сервер проверяет размеры
входов до отправки и выходов после. Если вызов не уложился во время, процесс убивается. Код:
[crates/ml](../../crates/ml/src/lib.rs).
