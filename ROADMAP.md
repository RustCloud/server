# RustCloud — планы

Что собираемся сделать и что ещё обсуждаем. Как пользоваться файлом:

- новая идея — пункт в подходящий раздел, спорное — в [Открытые вопросы](#открытые-вопросы);
- решили — переносим ответ к пункту, вопрос удаляем;
- сделали — удаляем пункт: история есть в git, а то, что уже работает, описано в [docs/](docs/README.md).

Принципы, которые новые возможности не нарушают, — в [docs/dev/architecture.md](docs/dev/architecture.md#принципы).

## Плагины

Цель: сторонние люди добавляют приложения (редактор документов, фотогалерею, календарь) и хуки
(уведомления, OCR) без пересборки сервера и клиентов.

### Решено

- **Ядро — тоже плагины.** `files` и будущие модули работают на том же контракте, что и сторонние
  плагины. Манифест и `GET /api/v1/apps` уже есть ([docs/api/apps.md](docs/api/apps.md)),
  боковая панель строится по ним.
- **Манифест** описывает всё, что сервер и клиенты знают о плагине:

  ```toml
  id = "docs-editor"
  version = "0.1.0"
  api = ">=1.2, <2"                # совместимые версии API сервера
  runtime = "wasm"                 # или "http" + адрес сервиса

  [name]                           # en обязателен
  en = "Document editor"
  ru = "Редактор документов"

  [requires]
  "rustcloud:files" = "^1"         # интерфейс другого плагина

  [permissions]                    # потолок прав; админ подтверждает при установке
  files = "opened"                 # opened | folder | all

  [settings]                       # те же типы полей, что у разделов настроек
  autosave_seconds = { kind = "number", unit = "s" }

  [[contributes."files.open_with"]]
  mime = ["application/vnd.oasis.opendocument.text", "text/markdown"]
  title = "Редактор документов"
  entry = "/edit"
  ```

- **Связь плагинов** — через сервер, не напрямую:
  - *интерфейсы*: плагин объявляет `provides`, другой — `requires`; каждый вызов проходит проверку
    прав и попадает в журнал;
  - *точки расширения*: `files` объявляет «Открыть с помощью…», редактор добавляет туда пункт;
  - *события*: плагины слушают события ядра и друг друга (`calendar.event_created`) —
    продолжение шины `audit!`.
- **Доступ к файлам выдаёт только пользователь.** Админ ставит плагин и утверждает потолок прав,
  но не может дать плагину доступ к чужим файлам — у него самого его нет.
- **Две формы доступа:**

  |                | Постоянный                          | На время открытия                       |
  |----------------|-------------------------------------|-----------------------------------------|
  | Пример         | фотогалерея индексирует папку «Фото» | редактор открыл документ                |
  | Область        | папка или все файлы пользователя    | один файл                               |
  | Заканчивается  | пользователь отзывает в настройках  | редактор закрыт                         |

  Доступ на время открытия держит клиент: подтверждает раз в ~30 с, при закрытии сообщает серверу
  и доступ отзывается сразу; без подтверждений — через ~2 мин; не дольше ~12 ч. Плагин сохраняет
  до закрытия — после закрытия запись отклоняется.
- **Согласие пользователя** при первом использовании: «Редактор получит доступ к открытому файлу
  на время редактирования. [Разрешить один раз] [Всегда разрешать]». «Всегда» убирает диалог,
  но не превращает доступ в постоянный. Постоянный доступ — отдельный диалог.
- **Плагин никогда не сильнее пользователя:** каждый вызов проверяет и доступ плагина,
  и `Files::check_access` от имени пользователя. Пользователя отключили или файл удалили — доступа нет.
- **Доступы** уже есть: таблица `app_grants`, API и «Настройки → Приложения с доступом»
  ([docs/api/grants.md](docs/api/grants.md)). Диалог согласия — вместе с «Открыть с помощью…».
- **Совместимость:** у сервера версия API плагинов (semver: минорные только добавляют); плагин
  объявляет совместимые версии. Несовместимый не ставится; после обновления сервера — отключается
  с предупреждением в админке и записью в журнале. Обновляет его админ.
- **Интерфейс плагина** — в `<iframe sandbox="allow-scripts">` без `allow-same-origin`: у страницы
  плагина нет нашего origin (ни cookie, ни прямых запросов к API), второй домен не нужен. Запросы
  к API идут через панель по `postMessage`, с токеном доступа плагина.
- **Замены стратегий** (S3, LDAP, OIDC) — в бинарнике, не плагинами: через них идёт каждый байт
  и каждый вход.

- **Кто пишет:** все, но пока только мы. SDK и документация для сторонних — когда откроем.
- **Первые плагины:** файлы, календарь (CalDAV), заметки.
- **Каталог плагинов** (решено 2026-11-05): `index.json` в репозитории
  [RustCloud/_plugins](https://github.com/RustCloud/_plugins), формат —
  [docs/dev/plugin-catalog.md](docs/dev/plugin-catalog.md). Ставит только администратор, как архив
  вручную; права — из манифеста в архиве, не из каталога. Архив — файл релиза по тегу, в записи
  размер и SHA-256; опубликованная версия не меняется. Подпись `index.json` (ed25519, ключ в сервере) —
  позже, до широкой публики.
- **Как запускаются:**
  - `files` — Rust-крейт в бинарнике (основная функциональность), но на том же контракте:
    манифест, `rustcloud:files` как интерфейс для других плагинов;
  - календарь, заметки и все следующие — **WASM**. API плагинов описан в WIT.
- **Скрытые файлы** — имя начинается с точки, как в Unix: так их понимают и WebDAV-клиенты, и ОС.
- **AppData** — у каждого пользователя своя **скрытая** папка данных для каждого плагина:
  - скрытые файлы не показываются, пока пользователь не включит «Показывать скрытые файлы»
    в настройках; тогда они видны полупрозрачными, AppData можно открыть и скачать;
  - при удалении плагина его AppData остаётся — пользователь сам забирает файлы,
    переустановленный плагин снова её видит;
  - плагин хранит там что угодно: календарь — файлы `.ics`, заметки — шаблоны, теги, индексы,
    настройки пользователя вроде темы;
  - доступ к своей AppData у плагина есть всегда, без диалога; к чужой AppData и к файлам
    пользователя — только по выданному доступу;
  - занимает место в квоте пользователя; в настройках плагина — «Место на диске: 321 МБ» и,
    если плагин разрешает, кнопка «Очистить данные»;
  - пользовательские настройки плагина (тема) — поля в манифесте, хранятся в AppData,
    форму рисует панель так же, как настройки сервера. Настройки уровня сервера — в админке.
- **Заметки** лежат в папках пользователя: он даёт доступ к папке (папкам), или плагин создаёт
  «Заметки» — это постоянный доступ к этой папке. Индексы и теги — в AppData.
- **Маршруты плагинов** — под `/app/<id>/`, внутри плагин отвечает на любые методы и пути сам:
  `PROPFIND /app/calendar/…` для CalDAV, JSON для своего интерфейса. Адреса обнаружения протоколов
  плагин просит в манифесте, ядро перенаправляет: `/.well-known/caldav → /app/calendar/`.
  Если адрес уже занят другим плагином, второй не ставится — с ошибкой, где названы адрес
  и плагин, который его занимает.
- **Календарь и заметки** поставляются с сервером и включены по умолчанию; админ может отключить.
- **Общий доступ к данным плагина** уже есть ([docs/api/app-shares.md](docs/api/app-shares.md)):
  пользователь делится папкой AppData (календарём) — просмотр или правка; плагин работает с ней
  от имени получателя через импорт `shares`. Учёт — «Настройки → Общий доступ к данным приложений»,
  выдача и отзыв — в журнале. Когда появятся настройки каждого плагина, раздел «Доступы» переедет туда.
  Группы — вместе с группами для файлов.
- **Пароли приложений** — как токены доступа в Git-хостингах: отдельный пароль на устройство или
  программу, с выбранными правами, отзывается отдельно. Права пока — по плагину и «чтение/запись»;
  дробнее (по папкам) — если понадобится.
  Нужны CalDAV, CardDAV, WebDAV — клиенты с Basic-аутентификацией не получают основной пароль.

- **Фоновые задачи плагинов** (индексация, обработка фото и видео, нейросети) — очередь в ядре:
  - **задача — один элемент** («обработать фото `<id файла>`») с ключом «вид + файл»: изменённый
    файл перезаписывает задачу, а не дублирует её. Плагин отвечает по каждой задаче отдельно —
    готово, ошибка, повторить позже; битый файл не роняет порцию;
  - **виды задач — в манифесте** (`[[jobs]]`): `kind`, размер порции `batch` (метаданные — 50,
    видео и нейросети — 5–10), лимиты на порцию `time_seconds` и `memory_mib`. Админ переопределяет
    их на вкладке «Плагины»;
  - **откуда задачи:** плагин ставит их, когда пользователь выдаёт доступ к папке (на всё, что уже
    лежит), дальше — события ядра (`file.created`, `file.changed` с фильтром `mime`) без вызова плагина;
  - **ядро раздаёт порции по кругу:** плагин → пользователь → вид задачи, чтобы 50 000 фото одного
    пользователя и тяжёлые нейросети не задерживали остальных. Экспорт вроде `run-batch`;
  - **число параллельных задач** — `[plugins] workers`, по умолчанию половина ядер, минимум 1.
    Плагин в порции уступает поток каждые 100 мс, чтобы задачи не тормозили ответы на запросы;
  - **от имени пользователя** и в пределах его доступа. Отозвал доступ, плагин отключили или
    удалили — его задачи отменяются;
  - **журнал сервера:** на каждую порцию строка — плагин, вид, пользователь, размер порции,
    сколько готово и с ошибкой, сколько осталось, время. Если «осталось» со временем не убывает —
    повод смотреть подробнее. Прогресс («1200 из 5000») — в админке и у пользователя.
- **Хранилище плагина** — общие данные плагина на уровне сервера: модели (распознавание лиц),
  справочники, кэш. Не AppData и не в квоте пользователей; лежит в `BlobStore` (потом и S3).
  Размер пока не ограничиваем; админ видит, сколько занято и что лежит, и может очистить.
  Только общее, не связанное с людьми — правило для авторов плагинов в `docs/dev/plugins.md`.
  - **Тяжёлые файлы скачивает ядро, когда плагин включён** — по списку `[[downloads]]` в манифесте
    (путь, адрес из `permissions.network`, сумма SHA-256); архив плагина остаётся маленьким. Потоком
    прямо в хранилище — модель не проходит через память песочницы. Ход загрузки — в админке;
    ошибка — причина и «Повторить».
  - Плагин читает большие файлы хранилища кусками (не больше предела данных за раз), для задач с
    моделями нужна своя `memory` в `[[jobs]]`. Модель грузится заново на каждую порцию — размер
    порции делит эту цену.

- **Лимиты плагина — три множителя к базе** (решено 2026-10-30): `[limits] memory, time, workers` в
  манифесте, администратор меняет их в «Расширенных настройках». Всё остальное считается из них,
  чтобы не было настроек, при которых плагин падает при любом поведении: память 64 МБ × `memory`,
  данные за вызов — четверть памяти (файл целиком, ответ `http`, миниатюра, тело запроса, мост),
  работа 10 с × `time`, общее время 60 с × `time` без времени инструментов `use.*`. Виды задач —
  множители к плагину. Защитные пределы (мегапиксели, переадресации, размеры ключей) не
  масштабируются. Лимита хранилища плагина нет и не будет.

- **Возможности сервера `use.*`** — тяжёлый нативный код, который ядро выполняет для плагинов вне
  WASM: `use.ffmpeg` (метаданные, миниатюры, кадры, позже перекодирование), `use.onnx`
  (нейросети по моделям из хранилища плагина) и другие. Список растёт вместе с проектом; каждая
  возможность описана в [docs/dev/use.md](docs/dev/use.md).
  - **Отдельный класс разрешений:** `[permissions] use = ["ffmpeg"]`, импорт `use-ffmpeg`
    (`rustcloud::app::use_ffmpeg::get_metadata(…)`). Админ утверждает включением, как сеть;
    обновление, которое добавило возможность, отключает плагин до подтверждения. Без разрешения —
    `not-allowed`; на сервере без инструмента — `unsupported`, `get-capabilities()` говорит, что есть.
    Плагин собирается без кода сервера, только по `app.wit`.
  - **Плагин просит намерение, а не команду:** в WIT только перечисления и числа в пределах, ни одной
    строки, которая попадёт в командную строку. Командную строку из шаблона собирает ядро.
  - **Слои защиты:** отдельный процесс на операцию через вспомогательный `rustcloud-sandbox` —
    rlimits (память, процессор, без файлов на запись), `no_new_privs`, seccomp (без сети, без
    `ptrace`, `mount`, `io_uring`…), Landlock (файловая система закрыта, кроме библиотек; запускать
    можно только сам инструмент), смерть вместе с сервером, таймаут по часам и предел вывода.
    Ввод и вывод — только трубы и открытый на чтение файл (`fd:`): путей инструмент не видит, ядро
    само открывает файл после проверки доступа и само пишет результат. **Файловую систему закрывает
    seccomp:** запрещены `open`/`openat` и все вызовы, которые создают, меняют и удаляют файлы, —
    поэтому инструмент собирается статически. Landlock — дополнительный слой, где ядро его включает:
    на ядре Proxmox его нет (проверено 2026-10-30, `EOPNOTSUPP`). Админ видит,
    какие слои действуют на этом сервере.
  - **ffmpeg своей сборки:** закреплённая версия, `--disable-everything --disable-network
    --disable-autodetect`, затем только нужные разборщики, декодеры, кодировщики и фильтры, протокол
    `pipe`; `-protocol_whitelist pipe`, белые списки форматов и кодеков, `-max_pixels`, `-threads`.
    Без `--enable-gpl`: лицензия LGPL, H.264-кодировщик решим при перекодировании (x264 — GPL,
    OpenH264 — BSD).
  - **Сначала `probe`, потом работа:** проверка разрешения, длительности, числа дорожек по
    потолкам `[media]` до тяжёлой операции; результат проверяется (сигнатура, размеры, объём).
  - **Свой пул и настройки:** `[media] workers`, память и время процесса, потолки входа;
    переполнение — `busy`, задача плагина уходит в `retry`.

## Открытые вопросы

### Плагины

- **Системные плагины.** Антивирусу или полнотекстовому поиску нужен доступ ко всем загрузкам,
  а админ чужие файлы не видит. Варианты: каждый пользователь соглашается сам; плагин видит
  файл только в момент загрузки и не может читать позже; таких плагинов нет.
- **Хуки с правом запрета** (проверить файл до сохранения): нужны ли, какой таймаут, что делать,
  если плагин упал — пропускать или отклонять.
- **Индексы на файлах.** Каждая запись файла — новый блоб целиком, поэтому большой индекс
  (или база SQLite в AppData) при каждом изменении переписывается полностью. Для календаря дома
  хватит мелких файлов (`.ics` на событие, индекс по месяцам). Если не хватит — добавить в AppData
  хранилище ключ-значение с выборкой по диапазону.
- **Сроки доступа на время открытия:** 30 с / 2 мин / 12 ч — подходят?

### Права администратора

- **Имена чужих файлов в журнале.** Админ не работает с чужими файлами, но в журнале видит
  «alice скачала report.pdf». Оставить, скрывать имена или настройкой?
- **Шифрование на диске.** Через RustCloud админ чужих файлов не откроет, но на сервере они лежат
  как есть. Нужно ли шифрование, при котором и владелец сервера их не прочитает?

### Клиенты

- **Нативные клиенты и интерфейс плагинов.** Произвольный интерфейс плагина нативно без пересборки
  не показать. Предложение: стандартные протоколы (WebDAV, CalDAV, CardDAV) → декларативные экраны,
  которые клиент рисует нативно → WebView для сложных плагинов. Допустим ли WebView?
- **Общее ядро клиентов** — библиотека на Rust (API, синхронизация, плагины) с нативным интерфейсом
  через UniFFI. Или каждый клиент отдельно?
