# Аудит безопасности RustCloud (ноябрь 2026)

Дата: 2026-11-04. Ревизия: `b3bc5e4`. Предыдущий отчёт — [SECURITY_AUDIT.md](SECURITY_AUDIT.md)
(2026-10-30). С тех пор появились песочница для ffmpeg, медиадвижок (миниатюры, HLS), нейросети
для плагинов (`use.onnx`), прокси к сервисам плагинов (`[[proxy]]`, WebSocket), ссылки и токены
приложений (`app-links`, WOPI) и тела запросов на диске (`large_bodies`).

**Метод:** код читался целиком по путям, которые трогают безопасность: вход и сессии, права на
файлы и гранты приложений, `/app/*`, прокси сервисов, ссылки приложений, мост панели и iframe,
WASM-хост, песочница, установка плагинов, Docker и CI. Нормализация путей в прокси проверена
отдельной программой на той же версии крейта `url`. Эксплойты против стенда **не запускались**.

## Итог

**Соответствует ли проект заявлениям.** Основа безопасности действительно сильнее средней:
обхода аутентификации, чтения чужих файлов, SQL-инъекций и выполнения кода на сервере не найдено.
Новый код написан аккуратно: подписи HMAC сравниваются за постоянное время, ссылки на загрузку
одноразовые, прокси не передаёт сервису cookie сессии и `Authorization`, у ffmpeg четыре
независимых слоя изоляции.

Но слова «безопасный» и «быстрый» верны только для небольшого доверенного круга
пользователей, а не для сервера в интернете:

- **Все 18 актуальных находок прошлого аудита не исправлены**, в том числе обе высокие (DoS через
  `/app/*` и через Argon2). Таймаутов соединений, общих лимитов параллельности и квоты по
  умолчанию по-прежнему нет.
- Найдена **новая высокая проблема**: любой пользователь двумя параллельными запросами
  «переместить» создаёт цикл в дереве папок. После этого запросы к этим папкам зацикливаются
  навсегда, и сервер можно положить.
- Прокси сервисов плагинов (Collabora и т. п.) — самая рискованная новая часть: ограничение по
  путям обходится через `%2e%2e`, а страницы сервиса работают на origin облака без песочницы.
- Цифры «быстрый» в README сняты одним пользователем. Под нагрузкой нет ни обратного давления, ни
  ограничений: Argon2, WASM-экземпляры и запросы к БД при обходе дерева (по запросу на уровень)
  растут без предела.

## Новые находки

### 1. [Высокий] Гонка при перемещении папок создаёт цикл в дереве

[service.rs:312](crates/files/src/service.rs#L312), [service.rs:540](crates/files/src/service.rs#L540)

`Files::update` сначала проверяет, что папка не перемещается внутрь самой себя (`is_inside`, по
запросу к БД на каждого предка), а потом отдельным запросом меняет `parent_id`. Транзакции и
блокировки нет. Два параллельных запроса `PATCH /api/v1/files/A {"parent_id": B}` и
`PATCH /api/v1/files/B {"parent_id": A}` оба проходят проверку, и получается `A → B → A`.

Последствия:
- папки A и B со всем содержимым пропадают из дерева пользователя (до корня их не дойти);
- `subtree()` обходит дерево по уровням и не помнит, где уже был. На цикле он не останавливается
  никогда, на каждом шаге делает запрос к БД и растит вектор. Этот обход вызывают удаление
  (`DELETE /api/v1/files/A`), копирование, перемещение в корзину, фоновые задачи по грантам;
- `ancestor_rows` упирается в `MAX_DEPTH` и отвечает внутренней ошибкой, так что доступ
  приложений к этим файлам тоже ломается.

**Сценарий:** любой пользователь (при открытой регистрации — кто угодно) делает цикл, затем
отправляет несколько `DELETE` на папку из цикла. Каждый запрос навсегда занимает задачу Tokio и
непрерывно нагружает БД, память растёт до OOM. Повторять можно бесконечно, перезапуск не помогает:
цикл остался в БД.

**Рекомендации:**
- проще всего — асинхронный мьютекс на владельца для изменений структуры дерева (перемещение,
  копирование, удаление): процесс сервера один, и проверка с записью станут атомарными и в SQLite,
  и в PostgreSQL. Если серверов когда-нибудь станет несколько — транзакция с
  `SELECT … FOR UPDATE` по цепочке предков;
- в `subtree()` хранить множество посещённых id и обрывать обход с ошибкой при повторе или после
  `MAX_DEPTH` уровней;
- миграцией или при старте находить узлы без пути к корню и возвращать их в корень (или в
  `lost+found`).

### 2. [Средний] Прокси сервисов: ограничение по путям обходится через `..` и `%2e%2e`

[service_proxy.rs:397](crates/server/src/service_proxy.rs#L397), [service_proxy.rs:481](crates/server/src/service_proxy.rs#L481)

Маршрут выбирается по сырому пути: `proxy_path_matches("/cool", "/cool/%2e%2e/admin")` → да.
Затем `target_url` склеивает `target + путь`, а reqwest разбирает строку как URL (крейт `url`,
WHATWG) и **схлопывает точечные сегменты, в том числе закодированные**. Проверено на `url 2.5.8`:

```text
/cool/../hosting/capabilities -> http://collabora:9980/hosting/capabilities
/cool/%2e%2e/admin            -> http://collabora:9980/admin
/cool/%2E%2E/%2e%2e/x?y=1     -> http://collabora:9980/x?y=1
```

Hyper и axum путь не нормализуют, а nginx перед сервером `%2e%2e` пропускает. Модуль обещает:
«only the paths the manifest lists, the rest of the service is out of reach». На деле любой
пользователь с открытым в плагине файлом достаёт **любой путь сервиса**: его админку,
служебные и отладочные эндпоинты (у Collabora это, например, `/browser/dist/admin/…`,
`/cool/getMetrics`; они под своим паролем, но становятся доступны для перебора и для
уязвимостей). Запрос при этом идёт с адресом и заголовками облака, а из-за п. 3 любая страница
сервиса выполняется на origin облака.

**Рекомендации:** перед сопоставлением отклонять (`400`) пути, где есть сегменты `.` и `..`, в
том числе закодированные (`%2e`, `%2E`), а также `%2f` и `%5c`. Либо нормализовать путь так же,
как это делает `url`, и сопоставлять и отправлять уже нормализованный путь. Добавить тест с
приведёнными строками.

### 3. [Средний] Страницы сервиса плагина работают на origin облака без песочницы

[AppFrame.svelte:287](web/src/components/AppFrame.svelte#L287), [service_proxy.rs](crates/server/src/service_proxy.rs)

Страницы WASM-приложений изолированы (CSP `sandbox` без `allow-same-origin`). Сервис из
`[[proxy]]` — наоборот: его страницы отдаются с origin облака, а панель показывает их в iframe с
`allow-scripts allow-same-origin allow-popups-to-escape-sandbox`. Скрипт сервиса имеет все права
страницы облака: он делает `fetch('/api/v1/…', {headers: {'X-Requested-With': '1'}})` с cookie
пользователя, проходит проверку CSRF и проверку `Origin` в прокси.

В документации это названо осознанным решением («approving the app means trusting the service»),
но последствия шире, чем доверие к одному плагину:
- **любая XSS в сервисе** (у LibreOffice Online и Collabora они бывали) превращается в XSS в
  облаке. Это полный захват аккаунта жертвы и, если жертва — администратор, установка
  плагинов и смена настроек;
- из-за п. 2 сюда попадают все страницы сервиса, а не только перечисленные пути;
- прокси пропускает все заголовки ответа сервиса, кроме hop-by-hop и чужих `Set-Cookie`:
  `Clear-Site-Data`, `Service-Worker-Allowed`, свой CSP. Со скриптом под своим путём и
  заголовком `Service-Worker-Allowed: /` сервис регистрирует service worker **на весь origin
  облака**: тот перехватывает все страницы и запросы панели и остаётся в браузере даже после
  удаления плагина.

**Рекомендации:** стратегически — отдавать сервисы с отдельного origin (поддомен
`office.cloud.example.com` или отдельный порт), как обычно и настраивают Collabora рядом с
Nextcloud. До этого: отфильтровать заголовки ответа сервиса по allowlist (как предлагает п. 9
прошлого отчёта), запретить `Service-Worker-Allowed`, явно показывать администратору при
одобрении, что сервис получает полный доступ к аккаунтам.

### 4. [Средний] Токен для одного файла через `x-rustcloud-send` отдаёт и другие файлы

[app_routes.rs:76](crates/server/src/app_routes.rs#L76), [app_routes.rs:130](crates/server/src/app_routes.rs#L130)

Внешний сервер (WOPI) получает токен `rct1.…` на **один** файл. Ограничение соблюдают только
импорты WASM (`ServicesFor::file_id`). Если приложение отвечает заголовком
`x-rustcloud-send: file:<id>`, сервер сам отдаёт файл через `links.send(user, app, target)`. Там
проверяется только, что у приложения есть грант на этот файл, а `token.f` не проверяется вообще:
claims токена в этот момент уже потеряны.

**Сценарий:** офисный плагин реализует WOPI `GetFile` как «взять id из пути
`/wopi/files/<id>/contents` и ответить `x-rustcloud-send: file:<id>`». Это естественная и самая
быстрая реализация. Пользователь открыл в редакторе один документ; тот, у кого оказался токен
(сам сервис, его логи, утёкший URL с `?access_token=`), подставляет другой id и скачивает любой
файл из папок, к которым у плагина постоянный доступ, вплоть до всех файлов пользователя.

**Рекомендация:** сохранять claims токена до ответа приложения и в `forward` отклонять
`Target::File(id)` с `id != token.f` (и `AppData`/`Storage`, если токену они не положены).
Заодно проверять `read_only`/`w`, если в будущем появится отправка с записью.

### 5. [Средний] `large_bodies`: тело запроса пишется на диск без квоты

[app_routes.rs:120](crates/server/src/app_routes.rs#L120), [app_bodies.rs:37](crates/server/src/app_bodies.rs#L37)

Для плагина с `large_bodies` тело больше `limits.data` пишется во временный файл
`data/tmp/request-bodies/…` целиком, ещё до вызова приложения. Предел — только
`files.max_upload_mib`, а по умолчанию он **не задан**. Квота пользователя, свободное место и
скорость передачи не проверяются. Обычные загрузки, наоборот, останавливаются по квоте прямо в
потоке (`Files::store`).

**Сценарий:** любой пользователь с сессией или паролем приложения с правом записи шлёт в
`/app/<плагин с large_bodies>/…` бесконечное тело (или несколько параллельных). Файл растёт, пока не кончится
место; БД SQLite, журнал и загрузки остальных начинают падать. Таймаутов нет (п. 3 прошлого
отчёта), так что запрос держится сколько угодно. Файл удаляется только после ответа приложения.

**Рекомендации:** ограничивать сохраняемое тело остатком квоты пользователя (оно всё равно
уйдёт в его файл) и разумным пределом по умолчанию, даже без `max_upload_mib`; не начинать
запись, когда на диске меньше N % свободного места; таймаут простоя на чтение тела.

### 6. [Низкий] Память фоновых задач не ограничена `max_memory`; обновления без одобрения

[plugins.rs:479](crates/server/src/plugins.rs#L479), [plugins.rs:944](crates/server/src/plugins.rs#L944)

- `job_config` перемножает множитель плагина (не больше `max_memory`) и множитель вида задачи
  из манифеста (`[[jobs]] memory`, до 64). Результат обрезается только по шкале, до ×64, то есть
  до **4 ГиБ на одну пачку**. Администратор ставит `max_memory = 4` (256 МиБ) и считает, что
  плагин больше не возьмёт, а задачи берут в 16 раз больше, да ещё по нескольку пачек сразу
  (`workers`).
- `asks_for_the_same` при обновлении сравнивает только `permissions`, `well_known`, `proxy` и
  `limits`. Новая версия без повторного одобрения может добавить `large_bodies` (п. 5), новые
  `[[jobs]]` с ×64 памяти и времени, `[[downloads]]` (загрузки с разрешённых хостов в хранилище
  без лимита, п. 16 прошлого отчёта) и `open_with`.

**Рекомендации:** ограничивать итог задач `max_memory` (или отдельной настройкой
`max_job_memory`); включить в сравнение `jobs`, `large_bodies`, `downloads`, `server_settings`.

### 7. [Низкий] Seccomp-фильтр — denylist без защиты от x32 ABI

[sandbox/src/linux.rs:81](crates/sandbox/src/linux.rs#L81)

Фильтр разрешает всё, кроме списка. `seccompiler 0.5` проверяет только `AUDIT_ARCH_X86_64` и не
отсекает номера с битом `__X32_SYSCALL_BIT` (`0x40000000`): x32-вызовы имеют ту же архитектуру
аудита и другие номера, поэтому `openat`, `socket` и `connect` через x32 проходят мимо фильтра.
Это работает только на ядрах с включённым x32 (`CONFIG_X86_X32_ABI` и `syscall.x32=y`; в Debian и
Ubuntu по умолчанию выключено). Но в Proxmox и многих контейнерах нет и Landlock — о чём
сказано в самом модуле, — и тогда скомпрометированный через вредоносное видео ffmpeg читает файлы
пользователя `rustcloud` (БД, `app-tokens.key`, все блобы).

Кроме того, `execve` разрешён: без Landlock процесс может стать другим статическим бинарником
(без `open` возможности у него маленькие, но это лишняя дверь).

**Рекомендации:** первым правилом фильтра отклонять `nr >= 0x40000000` (так делает systemd).
`execve` закрыть одним seccomp нельзя (он нужен, чтобы стать инструментом), поэтому без Landlock
это остаточный риск: показывать предупреждение в `/api/v1/admin/use/ffmpeg` и в журнале при
старте, когда Landlock нет, и советовать в документации ядро или контейнер с ним.

### 8. [Низкий] Исходники ffmpeg скачиваются без проверки контрольных сумм

[docker/build-ffmpeg.sh:23](docker/build-ffmpeg.sh#L23)

`fetch` скачивает dav1d, OpenH264 и ffmpeg по HTTPS и сразу распаковывает и собирает их. Хешей
нет. ffmpeg — единственная часть, которая разбирает недоверенные файлы пользователей на C, а
сборка релиза (`release.yml`) кешируется в GHA, так что подменённый один раз архив остаётся в
образах надолго. Базовые образы тоже без digest (`alpine:3`, `clux/muslrust:stable`,
`node:24-alpine`).

**Рекомендации:** зашить SHA-256 каждого архива в скрипт и проверять `sha256sum -c`;
закрепить образы по digest хотя бы в release.

### 9. [Низкий] Обход дерева — запрос к БД на уровень, гранты не ограничены

[service.rs:516](crates/files/src/service.rs#L516), [grants.rs:229](crates/files/src/grants.rs#L229)

`ancestor_rows` делает отдельный `SELECT` на каждого предка (до 256). `app_may_access`, `grant_for`
и `grant_covers` вызывают его **для каждого гранта** приложения, а число грантов на пользователя
не ограничено. Каждый вызов `active_grant_rows` к тому же читает все гранты пользователя и
удаляет истёкшие.

**Сценарий:** пользователь создаёт папки глубиной 250 и тысячи грантов одному приложению; каждое
обращение приложения к файлу стоит сотни тысяч запросов к БД. Это и прямой DoS, и ответ на
вопрос «быстрый ли он»: время доступа приложения к файлу растёт как глубина × число грантов.

**Рекомендации:** рекурсивный CTE (`WITH RECURSIVE`, есть и в SQLite, и в PostgreSQL) для
предков и поддерева — один запрос вместо сотни; предел числа грантов на пару
(пользователь, приложение); проверять предков один раз и сравнивать с множеством id грантов.

### 10. [Инфо] Отключённый аккаунт выдаёт, верен ли пароль

[service.rs:246](crates/auth/src/service.rs#L246)

`sign_in` вызывается после проверки пароля, и отключённый аккаунт с верным паролем получает
`403 ACCOUNT_DISABLED`, а с неверным — `401 INVALID_CREDENTIALS`. Для отключённого после
взлома аккаунта это оракул: подбирать пароль можно дальше (с лимитером), а результат пригодится
на других сервисах. Достаточно отвечать одинаково.

### 11. [Инфо] Ссылки приложений живут, пока жива сессия, и открыты CORS для всех

[app_links.rs](crates/server/src/app_links.rs), [network.rs](crates/server/src/network.rs) (`cors`)

Ссылка `/api/v1/app-links/<token>` на файл не имеет срока: она работает до выхода из сессии,
изменения файла или перезапуска сервера, то есть до 14 дней. Это bearer-токен с
`Access-Control-Allow-Origin: *`: страница приложения может передать его куда угодно, а
утёкшую ссылку (из логов прокси, истории) можно читать с любого сайта. Стоит добавить срок
(например, 12 ч, как у токенов WOPI) в claims.

## Что сделано хорошо (проверено в новом коде)

- **Песочница инструментов:** rlimits, `no_new_privs`, seccomp (файлы, сеть, процессы, сигналы
  чужим, `io_uring`, `ptrace`, `process_vm_*`, `pidfd_*`), Landlock; i386-вызовы через `int 0x80`
  убивают процесс (проверка архитектуры); окружение очищается перед `exec`; ffmpeg собран без
  сети, протоколов и лишних форматов.
- **Ссылки и токены приложений:** HMAC-SHA256 (проверен по RFC 4231), сравнение за постоянное
  время, разные наборы полей у разных видов токенов (одни не проходят за другие), ссылки на
  загрузку одноразовые и с 15-минутным сроком, при каждом обращении заново проверяются сессия,
  плагин, грант и версия файла; ключ токенов WOPI создаётся атомарно с правами `0600`.
- **Прокси сервисов:** только cookie-сессия и только при открытом файле; `Origin` обязателен для
  WebSocket и изменяющих запросов; cookie сессии и `Authorization` не уходят сервису; сервис не
  может поставить cookie сессии или cookie с `Domain`; лимиты соединений, запросов и размера
  тела; редиректы без следования; WebSocket закрывается, когда файл закрыт.
- **Мост панели:** `event.source` проверяется, запросы страницы только к `/app/<id>/` после
  нормализации URL, заголовки по allowlist, сервисы открываются только с одобренных origin.
- **Отправка файлов для приложений** (`x-rustcloud-send`) идёт через `content::serve`: HTML и SVG
  всегда с CSP `sandbox`, даже если приложение поменяло `Content-Disposition`.
- Пути прокси не могут занять `api`, `app`, `assets`, `health`; интерфейс использует хеш-роутер,
  поэтому свои страницы панели прокси перехватить не может.
- Сырого SQL с пользовательскими данными нет; поиск по `LIKE` экранируется.
- Разбор RRULE ограничен 500 повторами; Markdown заметок экранирует сырой HTML и отбрасывает
  опасные схемы ссылок.

## Предлагаемый порядок исправлений

1. **П. 1 этого отчёта** (цикл в дереве): транзакция с блокировкой при перемещении и защита
   `subtree()` от повторов — короткая правка, которая закрывает простой способ положить сервер.
2. **DoS из прошлого отчёта (пп. 1–4):** таймауты hyper, семафор на Argon2, лимит
   параллельности и тела на `/app/*`, `Yield` для WASM. Без этого сервер нельзя держать
   открытым в интернет.
3. **Прокси сервисов (пп. 2, 3):** отклонять точечные сегменты, allowlist заголовков ответа;
   стратегически — отдельный origin для сервисов и приложений.
4. **П. 4 и п. 5:** проверка `token.f` при `x-rustcloud-send`, квота для `large_bodies`.
5. **Логика из прошлого отчёта (пп. 5, 7, 8):** отзыв паролей приложений, атомарная квота и
   квота по умолчанию, изоляция `.appdata`.
6. Остальное по мере работы; seccomp — отсекать x32 одним правилом.
