# Аудит безопасности RustCloud

Дата: 2026-10-30. Ревизия: `5e4111a` (код тот же, что в `af0ccf3`: новый коммит меняет только
`ROADMAP.md`). Метод: чтение кода, без запуска эксплойтов против стенда. Незакоммиченный код
(`crates/sandbox/`, `docker/`, правка `Cargo.toml`) в аудит **не входил**: над ним сейчас идёт работа.

## Итог

Критических уязвимостей (обход аутентификации, чтение чужих файлов, выполнение кода на сервере)
**не найдено**. Основа сделана хорошо: единая проверка прав, токены хранятся только хешами, CSRF
закрыт, пользовательский контент и страницы плагинов изолированы CSP `sandbox`, пути к блобам
проверяются, архивы плагинов распаковываются безопасно.

Главные риски — **доступность (DoS)** у публичного сервера и несколько **логических недочётов**:
пароли приложений переживают смену пароля, у плагинов есть путь к SSRF через DNS, данные одних
приложений видны другим.

## Находки

### 1. [Высокий] Анонимные запросы к `/app/*` держат в памяти до ~48 МиБ каждый, без ограничения числа

[app_routes.rs:86](crates/server/src/app_routes.rs#L86), [app_routes.rs:171](crates/server/src/app_routes.rs#L171)

`forward()` пропускает запросы без сессии (решать будет приложение), читает тело целиком
(`BODY_LIMIT` = 16 МиБ), копирует его ещё раз (`body.to_vec()`) и передаёт в новый экземпляр WASM
(ещё одна копия в линейной памяти, лимит 64 МиБ). Аутентификации для этого не нужно: хватит
любого существующего приложения, например `POST /app/calendar/x` с телом 16 МиБ.

**Сценарий:** 100 параллельных анонимных запросов по 16 МиБ дают ~4–5 ГБ RAM, и процесс убивает
OOM. Ограничений по числу одновременных запросов, по IP или по приложению нет.

**Рекомендации:**
- для запросов без пользователя ставить маленький лимит тела (например 64 КиБ) или не читать
  тело, пока приложение не объявило в манифесте, что принимает анонимные запросы;
- не копировать тело второй раз (передавать `Bytes`, `into()` без `to_vec()`);
- `tower::limit::ConcurrencyLimitLayer` или семафор на `/app/*`: общий и на одно приложение.

### 2. [Высокий] Вход: Argon2 (19 МиБ) на каждую попытку без общего ограничения параллельности

[secret.rs:33](crates/auth/src/secret.rs#L33), [service.rs:208](crates/auth/src/service.rs#L208)

Каждая попытка входа, даже под несуществующим именем, запускает Argon2id (19 МиБ памяти, ~десятки
мс CPU) в `spawn_blocking`. Пул блокирующих потоков Tokio — до 512 потоков, то есть до ~10 ГБ
памяти в пике. Лимитер проверяет счётчик **до** проверки пароля, а записывает неудачу **после**,
поэтому пачка параллельных запросов с одного IP проходит вся. Глобального ограничения нет.

**Сценарий:** несколько сотен параллельных `POST /api/v1/auth/login` с разными именами занимают все
ядра и много гигабайт памяти; сервер перестаёт отвечать всем.

**Рекомендации:** глобальный `tokio::sync::Semaphore` на хеширование (например, по числу ядер),
а при его исчерпании отвечать `429`, а не ставить в очередь. Считать попытку до запуска хеширования
(резервировать слот в лимитере). То же для `change_password` и `update_account`.

### 3. [Средний] Нет таймаутов HTTP-соединений (slowloris)

[main.rs:59](crates/server/src/main.rs#L59)

`axum::serve` (0.8.9) не настраивает таймер hyper, поэтому нет ни `header_read_timeout`, ни
таймаута простоя. Загрузка файлов и тела запросов тоже читаются без таймаута.

**Сценарий:** тысячи соединений, которые шлют заголовки по байту, исчерпывают файловые дескрипторы
и память. Если сервер стоит за nginx или Caddy, тот частично закрывает проблему, но `compose.yml`
предлагает и прямой вариант `8080:8080`.

**Рекомендации:** собрать сервер через `hyper_util::server::conn::auto::Builder` с `TokioTimer` и
`header_read_timeout`; на загрузки поставить таймаут простоя (как `IDLE_LIMIT` у скачиваний
плагинов). В docs/install.md явно сказать, что прокси обязателен, если это решение.

### 4. [Средний] Код WASM-плагина блокирует поток Tokio на всё время лимита

[wasm-host/src/lib.rs:321](crates/wasm-host/src/lib.rs#L321)

Для обычных запросов `epoch_deadline_callback` возвращает `UpdateDeadline::Continue`: экземпляр
не уступает поток до конца лимита (`time_seconds`, по умолчанию 10 с, админ может поставить до 600).
Фоновые задачи уступают (`Yield`), запросы — нет.

**Сценарий:** приложение с дорогим путём (ошибка в плагине, тяжёлая развёртка `RRULE` и т. п.):
N параллельных запросов, где N — число рабочих потоков Tokio (по ядрам), замораживают весь сервер,
включая вход и файлы, на 10 с и больше. Повторяя запросы, сервер можно держать недоступным
постоянно. Вредоносный плагин может делать это сам.

**Рекомендации:** `UpdateDeadline::Yield(1)` и для запросов (async-поддержка в wasmtime уже
включена) либо выполнять экземпляры на отдельном пуле или `spawn_blocking`; ограничить число
одновременных экземпляров на приложение.

Попутно ([lib.rs:401](crates/wasm-host/src/lib.rs#L401)): `StoreLimits` ограничивает только размер
**одной** линейной памяти. Число памятей, таблиц и экземпляров и размер таблиц остаются по
умолчанию: компонент из нескольких core-модулей может занять память, кратную лимиту. Стоит задать
`memories(…)`, `tables(…)`, `table_elements(…)`, `instances(…)`.

### 5. [Средний] Пароли приложений не отзываются при смене или сбросе пароля

[service.rs:318-331](crates/auth/src/service.rs#L318-L331), [service.rs:378](crates/auth/src/service.rs#L378)

`change_password` удаляет остальные сессии, а сброс пароля админом удаляет все сессии. Таблицу
`app_passwords` не трогает ни то, ни другое. Создать пароль приложения можно одной сессией, без
повторного ввода пароля.

**Сценарий:** злоумышленник получил сессию (украденный токен или забытый чужой браузер) и создаёт
пароль приложения для `calendar` и `notes` с правом записи. Владелец замечает и меняет пароль:
сессии злоумышленника гаснут, а пароль приложения продолжает работать без срока.

**Рекомендации:** при смене или сбросе пароля отзывать пароли приложений или хотя бы явно
предлагать это в интерфейсе; требовать текущий пароль при создании пароля приложения; записывать
в журнал создание с IP.

### 6. [Средний] SSRF: правила сети плагина проверяют имя хоста, а не IP-адрес

[wasm-host/src/http.rs:132](crates/wasm-host/src/http.rs#L132), [plugin-api/src/network.rs](crates/plugin-api/src/network.rs)

Админ одобряет, например, `api.example.com`. Проверяется только имя в URL, а адрес резолвит
reqwest. Владелец DNS-зоны (автор плагина) может направить это имя на `127.0.0.1`,
`169.254.169.254`, адрес PostgreSQL или другого сервиса в LAN, в том числе через DNS rebinding между
проверкой и запросом. Ответ возвращается плагину целиком.

**Сценарий:** плагин «переводчик» с правилом `api.translator.example` читает
`http://api.translator.example:80/…` → `127.0.0.1:5432`/внутренние HTTP-сервисы (метаданные облака,
админки в LAN) и передаёт данные наружу через тот же разрешённый хост.

**Рекомендации:** резолвить имя самим (`reqwest::ClientBuilder::dns_resolver` со своим
резолвером) и отклонять loopback, link-local, private, CGNAT, multicast и unspecified адреса
(v4 и v6, включая v4-mapped), если правило не задано **явным IP-литералом**, как
`http://192.168.1.10:11434`. Заодно выключить системные прокси (`.no_proxy()`), чтобы `HTTP_PROXY`
из окружения не менял маршрут.

### 7. [Средний] Гонка квоты; по умолчанию нет ни квоты, ни лимита размера загрузки

[service.rs:505-506](crates/files/src/service.rs#L505-L506), [files/src/settings.rs:11](crates/files/src/settings.rs#L11)

Остаток квоты считается один раз в начале загрузки, поэтому N параллельных загрузок могут превысить
квоту в N раз. То же у `copy` и записей приложений. Кроме того, по умолчанию `default_quota_mib` и
`max_upload_mib` не заданы.

**Сценарий:** любой пользователь (при открытой регистрации — любой желающий) забивает диск, и
сервер перестаёт писать: БД SQLite, журнал, файлы остальных.

**Рекомендации:** резервировать место атомарно (счётчик «занято + в процессе» на пользователя,
обновляемый в транзакции, или проверка после записи с откатом); в примере конфигурации и
документации рекомендовать квоту по умолчанию; держать запас свободного места (отказывать в
загрузке, когда на диске осталось меньше X %).

### 8. [Средний] Приложение с доступом к корню или папке выше видит `.appdata` всех других приложений

[grants.rs:166](crates/files/src/grants.rs#L166), [appdata.rs](crates/files/src/appdata.rs)

AppData — обычная скрытая папка `.appdata/<app>` в дереве пользователя. `app_may_access` проверяет
только, лежит ли узел внутри выданной папки. Если выдать приложению B доступ «все файлы»
(`FileScope::All`), B читает и **меняет** данные приложения A: календари, заметки, а в будущем,
возможно, токены и секреты. При этом модуль сам пишет: «The app reaches only its own folder».
Для фоновых задач скрытые папки уже исключены (`granted_files`), а для прямого доступа — нет.

**Рекомендации:** в `app_may_access` и `app_children` отклонять узлы внутри `.appdata` (кроме
собственной папки приложения через AppData API); в диалоге выдачи доступа к корню предупреждать.

### 9. [Низкий] Ответы плагинов могут ставить любые заголовки

[app_routes.rs:175-188](crates/server/src/app_routes.rs#L175-L188)

Отфильтрованы только `Set-Cookie`, `Content-Security-Policy` и `X-Frame-Options`. Плагин может
вернуть:
- `Clear-Site-Data: "cookies", "storage"` — разлогинить пользователя на всём домене облака;
- `Strict-Transport-Security: max-age=…; includeSubDomains` — навязать HSTS всему домену;
- `Access-Control-Allow-Origin: https://evil` + `Access-Control-Allow-Credentials: true` — CORS-доступ
  к своим ответам (опасно вместе с п. 15);
- `Content-Security-Policy-Report-Only`, `Refresh`, `Link`, `Service-Worker-Allowed` и т. п.

**Рекомендации:** перейти на allowlist: `Content-Type`, `Content-Length`, `Cache-Control`, `ETag`,
`Last-Modified`, `Location`, `Content-Disposition`, DAV-заголовки (`DAV`, `Allow`, `Content-Range`…).

### 10. [Низкий] Блокировка чужого аккаунта неудачными входами

[service.rs:208](crates/auth/src/service.rs#L208), [app_passwords.rs:152](crates/auth/src/app_passwords.rs#L152)

10 неудачных попыток с разных IP блокируют вход по имени на 15 минут, и так можно повторять
бесконечно. Для `app-password:<user>` тоже: CalDAV-клиенты жертвы перестают синхронизироваться.

**Рекомендации:** не блокировать вход с IP, с которого уже был успешный вход (доверенное
устройство), или заменить блокировку растущей задержкой; не считать неудачи пароля приложения,
если такого хеша нет вообще (подобрать 256-битный токен нельзя, его перебор не нужно
ограничивать по имени).

### 11. [Низкий] PDF отдаются inline с основного origin без CSP

[content.rs:106](crates/files/src/content.rs#L106)

Для `application/pdf` не ставится `sandbox`, файл открывается inline с домена облака, в том числе
по публичной ссылке. Встроенные просмотрщики изолированы, но у pdf.js в Firefox были уязвимости
с выполнением JS (CVE-2024-4367). Атакующий пользователь может прислать ссылку на свой PDF.

**Рекомендации:** для публичных ссылок отдавать PDF как `attachment` или с отдельного домена для
пользовательского контента (это вообще лучший вариант для облака); как минимум держать в
документации требование к актуальным браузерам.

### 12. [Низкий] Публичные ссылки работают после отключения аккаунта владельца

[shares.rs:150](crates/files/src/shares.rs#L150)

`open_share` не проверяет `owner.disabled`. Если аккаунт отключили (взлом, раздача вредоносных
файлов), его ссылки продолжают отдавать файлы. Общий доступ к данным приложений, наоборот, такой
аккаунт уже учитывает (`share_owner`).

**Рекомендация:** проверять владельца в `open_share`.

### 13. [Низкий] Токены публичных ссылок хранятся в БД открытым текстом

[shares.rs:56](crates/files/src/shares.rs#L56)

Сессии и пароли приложений хранятся хешами, а токены ссылок — нет. Утечка резервной копии БД
даёт доступ ко всем расшаренным файлам. Владельцу ссылку показывают повторно (`GET /api/v1/shares`),
поэтому простой хеш сломает интерфейс.

**Рекомендация:** хранить SHA-256 и показывать ссылку только при создании (как пароль приложения)
или шифровать токен ключом из конфигурации.

### 14. [Низкий] Перебор имён пользователей

[app_shares.rs:90](crates/files/src/app_shares.rs#L90)

`POST /api/v1/app-shares` отвечает `USER_NOT_FOUND` или успехом, и любой пользователь может
проверить, существует ли имя (а заодно, отключён ли аккаунт). Для облака «для семьи» это
приемлемо, для публичного сервера — утечка списка аккаунтов.

### 15. [Низкий] Basic-аутентификация обходит проверку CSRF

[app_routes.rs:69](crates/server/src/app_routes.rs#L69), [calendar/src/dav.rs:53](apps/calendar/src/dav.rs#L53)

`X-Requested-With` требуется только у cookie-сессий. CalDAV отвечает `401` с `WWW-Authenticate`;
если пользователь открыл адрес DAV в браузере и ввёл пароль приложения, браузер запоминает Basic-
данные и подставляет их и в межсайтовые запросы (POST-формы). Сейчас риск мал: notes/calendar
ждут JSON или DAV-методы. Но это ловушка для будущих плагинов.

**Рекомендация:** для Basic-запросов с методами, которые меняют данные, требовать отсутствие
`Origin`/`Sec-Fetch-Site: cross-site` (DAV-клиенты их не шлют).

### 16. [Низкий] Хранилище и очередь задач плагинов не ограничены

[plugin_storage.rs:7](crates/server/src/plugin_storage.rs#L7), [plugin_jobs.rs:145](crates/server/src/plugin_jobs.rs#L145)

`storage.write` плагина не ограничено по объёму («There is no size limit yet»), а `jobs.add`
принимает по 1000 задач за вызов без общего лимита на пользователя. Через приложение (или ошибку
в нём) любой пользователь может наполнить диск или таблицу `plugin_jobs`.

**Рекомендация:** квота на хранилище плагина (в манифесте + решение админа) и предел числа
ожидающих задач на пару (приложение, пользователь).

### 17. [Низкий] Первый зарегистрированный становится админом; DNS rebinding по умолчанию

[service.rs:156](crates/auth/src/service.rs#L156), [network.rs](crates/server/src/network.rs) (`only_listed_urls = false`)

Пока аккаунтов нет, любой, кто первым откроет сервер, становится администратором. При
`only_listed_urls = false` сайт в интернете через DNS rebinding может сделать это из браузера
пользователя в LAN (сервер только что поднят и ещё не настроен).

**Рекомендации:** одноразовый setup-токен, который печатается в лог при первом запуске; либо
включать `only_listed_urls` по умолчанию, когда задан `public_url`.

### 18. [Низкий] `Secure` у cookie зависит от настройки; нет HSTS

[auth/src/http.rs:178](crates/auth/src/http.rs#L178)

`Secure` ставится, только если `public_url` начинается с `https://` или доверенный прокси прислал
`X-Forwarded-Proto: https`. За TLS-прокси без этих настроек cookie сессии уходит без `Secure`.
Заголовка `Strict-Transport-Security` сервер не ставит.

**Рекомендации:** предупреждать в журнале при старте («запрос пришёл через прокси, но
`trusted_proxies` пуст»); ставить HSTS, когда `public_url` — https.

### 19. [Низкий] CI: адрес реестра из ответа по HTTP, отключение проверки TLS

## 20. Информационно и защита в глубину

- **`LocalBlobStore::copy`** ([storage-local/src/lib.rs:120](crates/storage-local/src/lib.rs#L120)):
  ключ `to` проверяется только в `publish`, **после** `fs::copy` во временный путь
  `tmp/{to}.part`. Сейчас ключи всегда UUID, но ключ вида `../../x` записал бы файл за пределы
  хранилища. Достаточно вызвать `self.blob_path(to)?` первой строкой, как в `put`.
- **Токен сессии в JSON-ответе на вход** — для браузера не нужен (есть HttpOnly-cookie), а при XSS
  его можно украсть. Можно отдавать токен только по запросу (`?token=1`) или только не браузерным
  клиентам.
- **Нет «выйти на всех устройствах»** и списка сессий. Это пригодится после п. 5.
- **`change_password` не ограничен по попыткам**: украденная сессия позволяет подбирать текущий
  пароль (медленно, из-за Argon2).
- **Журнал** записывает введённое имя при неудачном входе. Если пользователь ввёл пароль в поле
  имени, пароль окажется в журнале. Обычная практика, но стоит знать.
- **Заметки**: в превью разрешены внешние `<img>`, и общая заметка может «звонить домой»
  (раскрывает IP читателя). Можно добавить `img-src 'self' data:` в CSP ответов приложений.
- **Образы без закреплённых версий** (`alpine:3`, `clux/muslrust:stable`, `node:24-alpine`,
  `:latest` в compose): это цепочка поставок. Стоит закрепить по digest, хотя бы для release.
- **Регистрация** (если открыта) без капчи и лимита — массовое создание аккаунтов.
- **CSP главной страницы** разрешает `script-src 'self'`, а под тем же origin по `/app/<id>/…`
  плагин может отдать JS. Если в интерфейсе когда-нибудь появится HTML-инъекция, CSP её не
  остановит: скрипт возьмут из `/app/…`. Отдельный домен для приложений закрыл бы и это, и п. 9,
  и п. 11.

## Что сделано хорошо (проверено)

- Права на файлы проверяются в одном месте (`Files::check_access`), чужие узлы отвечают как
  несуществующие, поиск и списки ограничены владельцем.
- Сессии и пароли приложений: 256-битные случайные токены, в БД только SHA-256; сессии
  отзываются при выходе, отключении и сбросе пароля.
- Argon2id; одинаковое время ответа для неизвестного пользователя (фиктивный хеш).
- CSRF: `SameSite=Lax` + обязательный `X-Requested-With`, CORS без credentials и без этого заголовка.
- `X-Forwarded-For` учитывается только от доверенных прокси, берётся правый недоверенный адрес.
- Пользовательский контент: HTML, SVG, JS всегда как `attachment`; inline-типы с CSP `sandbox`;
  `nosniff`; корректный `Content-Disposition` (RFC 6266).
- Страницы плагинов: CSP `sandbox` без `allow-same-origin`, `frame-ancestors 'self'`, cookie и
  `Authorization` к плагину не передаются; мост postMessage проверяет `event.source` и не выпускает
  запросы за пределы `/app/<id>/` (URL нормализуется перед проверкой).
- Имена файлов и пути AppData/хранилища плагинов валидируются (`..`, `/`, `\`, управляющие символы).
- Ключи блобов ограничены `[A-Za-z0-9-]`.
- Zip плагинов: `enclosed_name`, ограничение глубины, лимиты размера при распаковке (защита от
  zip-бомб), установка через скрытую папку и `rename`.
- Id плагина ограничен `[a-z0-9-]`, поэтому `install_dir.join(id)` безопасен.
- Обновление плагина, которое просит больше прав, снова требует одобрения админа; секреты
  плагинов не отдаются в браузер.
- Редиректы HTTP плагинов проверяются по правилам на каждом шаге, `Authorization`/`Cookie`
  снимаются при смене хоста.
- WASI без файлов, сети и окружения; лимиты памяти и времени; фоновые задачи уступают поток.
- Внутренние ошибки не раскрывают деталей клиенту.
- Markdown в заметках: сырой HTML превращается в текст, `javascript:` и подобные схемы
  отбрасываются.
- Файл конфигурации пишется атомарно с правами `0600`; Docker: не-root, `read_only`,
  `cap_drop: ALL`, `no-new-privileges`, порт только на `127.0.0.1`.
